# Section 7 Test Design and Prototype Mismatches

This document records differences found while implementing the twelve test cases from Section 7 of the updated Quality Assurance Mid-Project Report. It describes the repository as inspected on 24 August 2026. No production code was changed while creating the tests.

## Summary

| Test case | Intended design | Current prototype | Automated-test treatment |
|---|---|---|---|
| TC-01 | A complete call submission creates one case and records all specified values. | The submission creates a case, but the timestamp is generated by the domain model rather than entered by the dispatcher. The generated identifier is a `Guid`, displayed as a shortened `CASE-XXXXXXXX` case number. | Verifies one stored case, all submitted values, the generated identifier, and a timestamp within the submission interval. |
| TC-02 | The UI rejects a blank location or no selected unit type and displays clear, actionable errors. | Razor Pages validation contains `[Required]` and `[MinLength(1)]`. The domain also rejects these values, but its location exception says only `This field is required`; that is clear but does not explicitly tell the user which corrective action to take unless the UI associates it with the field. | Automates the domain rejection and confirms no case is stored. Final wording and absence of technical details still require a rendered UI/system test. |
| TC-03 | One submission creates, prioritises, routes, stores, and assigns a multi-department case. | `CreateAndDispatch` performs these operations in one call. Routing is represented by `RequiredUnitTypes` and department dashboard filtering; there is no separate routed case copy or department endpoint. | Verifies one stored case, calculated priority, both assignments, unit availability, and `InProgress` state. |
| TC-04 | Priority follows approved Medical, Police, and Fire decision processes in Appendix 1. | Appendix 1 names the diagrams but does not contain their rules. `KeywordSeverityPriority` is an explicitly labelled prototype policy based on keywords and the dispatcher-entered severity. It is not department-specific. | Data-driven tests cover the implemented placeholder policy. They cannot prove compliance with the intended Appendix 1 rules. Replace the data and strategy tests when those rules are supplied. |
| TC-05 | A case is delivered to three independent department endpoints within two seconds, with sender/receiver copies compared. | Departments are in-memory domain objects. No network delivery, endpoint acknowledgement, serialisation, or separate receiver copy exists. | Measures the complete in-process `CreateAndDispatch` call, verifies all three required department assignments, and compares the resulting case with the request. This is useful prototype evidence but not an endpoint-routing performance test. |
| TC-06 | Assignment skips an unavailable unit and chooses the first available unit in department order. | This behaviour is implemented by `FirstOrDefault` over the department unit list. | Fully automated with P-01 occupied and P-02/P-03 available. |
| TC-07 | A waiting case is processed when a unit is manually changed to available and the queue is processed again. | Availability is intentionally controlled by assignment/sign-off. Users cannot directly mark an assigned unit available. `SignOffUnit` releases the unit and immediately assigns it to the oldest compatible waiting case. | Uses the implemented sign-off flow and verifies automatic assignment to the waiting case. The report steps should be revised if they are intended to describe the current prototype. |
| TC-08 | Two assignment requests target one available unit simultaneously. | Assignment is serialised by `DispatchService` using `_dispatchLock`, and `Unit.TryAssign` also refuses unavailable units. | Starts two submissions together and verifies one active assignment, one open waiting case, and two intact stored cases. Thread scheduling cannot guarantee that both operations enter the lock at the exact same CPU instant, but the shared start gate exercises the race boundary. |
| TC-09 | An already-open dashboard updates automatically when cases or mutable case information change. | The dashboard uses a full-page reload every five seconds. Case priority and location are immutable after creation, so the report step that changes either value from another session cannot currently be performed. | Automates the department filtering and verifies a fresh projection includes the new Police case and excludes Fire-only cases. Browser-level polling and live mutation remain unautomated because the required mutation does not exist. |
| TC-10 | A multi-unit case remains `InProgress` until the final unit signs off. | Implemented by the case aggregate and `DispatchService.SignOffUnit`. | Fully automated, including each unit's availability transition. |
| TC-11 | Removing all assigned units before completion returns the case to `Open`. | `Case.Unassign` implements this domain behaviour, but there is no current UI or application-service action that invokes it. | Automates the domain transition. The system-level test cannot be completed until an authorised removal workflow exists. |
| TC-12 | Dispatcher, department, and response-unit users see only permitted features and cannot directly access another role's pages. | Cookie authentication, scoped demo accounts, conditional navigation, and `RoleAccessMiddleware` are implemented. | Automates the middleware access matrix for allowed and denied dispatcher, department, and response-unit paths. Visual checks of each tailored interface remain suitable for a manual system test. |

## Additional requirement observations

- Section 7 uses “UUID” for the case identifier. The implementation stores a .NET `Guid`, which is UUID-compatible, but users normally see only the shortened `CASE-XXXXXXXX` value.
- TC-01 says the system assigns “the suitable units.” The implementation selects the first available unit for each required department; it does not calculate suitability using distance, personnel count, or incident capability.
- TC-03 expects High reported severity for a vehicle collision. The current keyword policy checks `collision` before falling back to reported severity, so the resulting priority is Medium. This matches the current code but may not match the intended priority design.
- The report alternates between “Ambulance” and “Medical.” The domain enumeration and department are named `Medical`; the UI describes Medical as ambulance and clinical response.
- The system uses in-memory repositories. Persistence assertions prove retention during the running process only; they do not prove recovery after restart or durable database storage.

## Follow-up needed for full design compliance

1. Supply and approve the Appendix 1 decision rules, then replace the TC-04 placeholder expectations.
2. Decide whether “routing” requires independent department delivery/acknowledgement or whether shared in-memory visibility is sufficient for the prototype.
3. Either add a supported case-update operation or revise TC-09 so it tests only new-case polling.
4. Either add an authorised unit-removal workflow or classify the system-level portion of TC-11 as outside the current prototype scope.
5. Run TC-02, TC-09, and TC-12 through a browser as manual acceptance checks to verify rendered validation text, five-second refresh behaviour, and role-specific navigation.
