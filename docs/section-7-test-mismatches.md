# Section 7 Test Design and Prototype Mismatches

This document records remaining differences between the prototype and Quality Assurance Mid-Project Report revision `-4`, including its completed appendices. The repository was reviewed on 25 August 2026. Appendix-defined priority and module-isolation behaviour was implemented, and Section 7 plus `PrototypeTesting.cs` were updated to follow the executable workflow.

## Summary

| Test case | Intended design | Current prototype | Automated-test treatment |
|---|---|---|---|
| TC-01 | A complete call submission creates one case and records all specified values. | The submission creates a case, but the timestamp is generated by the domain model rather than entered by the dispatcher. The generated identifier is a `Guid`, displayed as a shortened `CASE-XXXXXXXX` case number. | Verifies one stored case, all submitted values, the generated identifier, and a timestamp within the submission interval. |

| TC-06 | Assignment skips an unavailable unit and chooses the first available unit in department order. | This behaviour is implemented by `FirstOrDefault` over the department unit list. | Fully automated with P-01 occupied and P-02/P-03 available. |

## Additional requirement observations

- Section 7 uses “UUID” for the case identifier. The implementation stores a .NET `Guid`, which is UUID-compatible, but users normally see only the shortened `CASE-XXXXXXXX` value.
- The report says unit suitability includes availability and distance. The implementation selects the first available unit in repository order; it does not compare unit distance, personnel count, or incident capability.
- Appendix 1 contains conditional phrases such as “fall (if the patient is conscious),” “seizure (if it has stopped),” and “small wildfire.” The data model has no separate consciousness, seizure-state, or fire-size fields, so the policy assumes the dispatcher records those conditions in the incident type or description. `small wildfire` is explicitly evaluated as Medium before the broader High `wildfire` term.
- Appendix 1 does not state how one global case priority should be selected when several requested departments produce different outcomes. The implementation uses the safest deterministic rule: the highest matching priority wins.
- The report alternates between “Ambulance” and “Medical.” The domain enumeration and department are named `Medical`; the UI describes Medical as ambulance and clinical response.
- The system uses in-memory repositories. Persistence assertions prove retention during the running process only; they do not prove recovery after restart or durable database storage.

## Follow-up needed for full design compliance

1. Clarify in the report that “routing” means shared in-memory visibility for selected departments, not network delivery to independent endpoints.
2. Replace statements that assignment considers distance with “first available unit in department list,” unless distance selection is planned after the prototype.
3. State whether the prototype-only Admin role is an intentional exception to Appendix 3. The report body describes it, but Appendix 3 lists only Dispatcher, Department, and Unit and says unlisted access is denied.
4. Define the expected multi-department priority rule explicitly. The implementation currently selects the highest match.
5. Run TC-02, TC-09, and TC-12 through a browser as manual acceptance checks to verify rendered validation text, the five-second refresh, and role-specific navigation.
